# Bundled licences and attribution (#70)

Everything the APK bundles that carries a licence — the app's own licence, its
Gradle dependencies, the vendored native libraries, the OCR/kana models and the
dictionary data derived from upstream corpora — ships inside the APK under
`app/src/main/assets/licenses/`, with an index and an in-app viewer reached from
the **Licenses** button on the main screen.

No network is involved, in the viewer or anywhere in this feature: the app declares
no `INTERNET` permission and none was added.

## Layout

```
app/src/main/assets/licenses/
  INDEX.txt                     the index the viewer reads (GENERATED)
  texts/                        licence texts, one file per licence
    apache-2.0.txt  apache-2.0-with-llvm-exception.txt  agpl-3.0.txt
    gpl-3.0.txt  lgpl-2.1.txt  mpl-2.0.txt  bsd-3-clause-ncnn.txt
    cc-by-sa-4.0.txt  unicode-licence-v3.txt  edrdg-licence.txt
    rust/                       per-crate texts from the Rust closure
  notices/                      attribution/provenance, one file per component family
app/licenses/                   generation inputs (not shipped)
  components.tsv                hand-maintained components
  maven.tsv                     dependency → licence mapping
  rust.tsv                      Rust crates (GENERATED by tools/gen_rust_license_bundle.py)
tools/gen_rust_license_bundle.py
```

`INDEX.txt` is TAB-separated with `#` comments, six columns:

```
name | licence label | version | licence text file(s) | notice file | provenance
```

`-` means absent. Paths are relative to `app/src/main/assets/`. The parser behind it
is `util/LicenseIndex.kt` (no Android types, so it is unit-tested) and the viewer is
`LicenseDialog.kt` — a component list and, below it, the selected component's notice
plus full licence text, each independently scrollable. Components share text files
rather than each carrying a copy, so the Apache-2.0 text appears once in the APK no
matter how many modules are under it.

## Regeneration

Three inputs, three generators. None of them is the build script: the build only
*reads* what they produced, and verifies it.

```sh
# 1. the index — hand components + resolved runtime classpath + Rust crate list
./gradlew :app:generateLicenseIndex

# 2. the Rust half — the crate closure of nav_graph_core, texts and rows
python3 tools/gen_rust_license_bundle.py        # needs cargo; any Python 3

# 3. the licence texts themselves — fetched by hand, once
#    (URLs are recorded per file: in the index's provenance column and in the
#     notice beside each component; the canonical ones are listed below)
```

**A dependency added without a notice fails the build.** `:app:verifyLicenseIndex`
is a `preBuild` dependency: it recomputes the index from the resolved
`debugRuntimeClasspath` and the three manifests and fails when the committed
`INDEX.txt` differs, naming what to run. Regeneration itself fails, before it
writes anything, listing every module with no entry in `maven.tsv`:

```
No licence notice for 1 dependency/dependencies on the runtime classpath:
  com.example:newthing:1.0.0
Add each one to app/licenses/maven.tsv (…)
```

That is the whole point of generating the dependency half: the list cannot rot
silently. `components.tsv`, `maven.tsv` and `rust.tsv` are the hand-maintained
residue — one row per component family, not per module.

The index is also checked for internal consistency by `LicenseIndexTest` (JVM unit
test): every entry names a licence and points at files that exist and are non-empty,
every canonical text file contains the licence it is labelled with, every
`Apache-2.0` entry ships the Apache text, and the AGPL copy is byte-identical to the
repository `LICENSE` (the generator rewrites it from there, so it cannot drift).

## The viewer

**MainActivity → Licenses** (`addButton(layout, "Licenses")`, beside Manage
Dictionaries) opens a dialog listing every component with its licence; selecting one
shows its notice, provenance and the full licence text. Everything is read from
assets, so it works with airplane mode on — and with the app's no-`INTERNET`
posture unchanged.

The EDRDG licence statement asks a smartphone app for exactly this: the
acknowledgement on a separate screen reached from a menu, not on a launch screen
("It is not sufficient just to mention it on a start-up/launch page of the app").
KRADFILE and JMdict-derived data ship in `assets/components` and `assets/variants`,
so that requirement applies here and this dialog is the screen that meets it.

## Out of scope

- The project's own licence is unchanged: `LICENSE` at the repo root stays AGPL-3.0,
  and the app's copy under `assets/licenses/texts/` is generated from it.
- Licences for **user-imported** dictionaries (JMdict/KANJIDIC Yomitan zips). Their
  notices live with the import; the app bundles no KANJIDIC data of its own.
- `models/archive/` and `tmp/` — not shipped, so not covered.

## Known gaps

- **The kana-size model's own terms are unstated.** Its provenance says "see the
  model author's INTERFACE_NB.md", which is not in this repository, so no licence
  text is shipped for the weights and the index labels that entry `Unstated in-repo`.
  The training corpora (Aozora, ja Wikipedia) *are* attributed, because that
  attribution is required regardless.
- **The deinflection table has no upstream revision pin.** `deinflect.json` is
  JSON-identical to `FooSoft/yomichan`'s `ext/data/deinflect.json` at master as of
  2026-09-13 (verified by comparing all 36 groups), and the project README credits
  Yomitan's rule files, but no commit hash for the source is recorded in this repo.
  The notice states exactly what was verified and when.
- **The Rust crate list is as wide as `cargo metadata` reports.** It includes the
  normal-dependency closure, which pulls in uniffi's `cli`/bindgen support crates
  that the shipped shared object probably does not reference. Over-attribution is
  the safe direction and the notice says so.
- **Licence labels are not SPDX expressions throughout.** The hand rows use readable
  labels (`CC-BY-SA-4.0`); the generated Maven and Rust rows carry `group:artifact`
  ids and SPDX expressions respectively. A future cleanup could normalise all three
  onto SPDX, but nothing reads them as SPDX today.
