EDRDG-derived data — KRADFILE components, JMdict kanji forms and kana variants
=============================================================================

Bundled as : app/src/main/assets/components/krad_components.txt

    Kanji decomposition table (12,156 kanji), built from EDRDG KRADFILE and
    KRADFILE2 by tools/build_component_table.py. Used to propose characters the
    recogniser cannot emit (issue #44).

    app/src/main/assets/variants/kanji_variants.txt

    669 variant→canonical pairs; one half from Unihan (see
    licenses/notices/unihan-variants.txt), the other half from JMdict's
    out-dated/rarely-used kanji tags (oK/rK) intersected with Unihan's
    simplified/traditional axis, built by tools/build_kanji_variants.py.

    app/src/main/assets/variants/kana_variants.txt

    16 variant→canonical kana pairs (historical kana orthography → modern), built
    from JMdict's own kana cross-references — readings of one entry that differ at
    a single position on a historical-kana row (かつかざん/かっかざん, あはれ/あわれ,
    あづま/あずま) — by tools/build_kana_variants.py (issue #75). Used to normalise a
    lookup query only; displayed text is never rewritten.

Note on KANJIDIC
----------------

The app bundles no KANJIDIC data. KANJIDIC entries reach the popup only through a
dictionary the user imports themselves, and those notices travel with the import;
they are deliberately not part of this bundle.
